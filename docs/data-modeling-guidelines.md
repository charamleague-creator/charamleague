# Data Modeling Guidelines

Convention บังคับสำหรับทุก feature ในโปรเจกต์นี้ สรุปจากบทเรียนของระบบเดิม (ดู `CHARAM-LEAGUE-สรุปบทเรียน-และข้อกำหนดระบบใหม่.md`)

## 1. ห้ามตัวนับสะสม (mutable counters)

อย่าเก็บค่าสรุป/โควตา (เช่น "ขายไปแล้วกี่ครั้ง") เป็นตัวเลขที่บวกทีละ 1 แล้วเก็บแยกไว้บนเอกสารทีม

**ให้ทำแทน:** คำนวณสดจาก query ต้นทางทุกครั้งที่ต้องใช้ (เช่น count จาก `transactions` collection ที่กรองด้วย `season` + `teamId`) เขียนเป็นฟังก์ชันคำนวณจุดเดียว แล้วใช้ทั้งตอน "แสดงผลบนหน้าจอ" และตอน "บังคับกฎ" (validate ก่อนเขียน) — ห้ามมี 2 สูตรที่ควรตรงกันแต่แยกกันเขียนคนละที่

## 2. แยก document ตามระดับสิทธิ์การเขียน

field ที่ "ใครก็แก้ได้บ่อยๆ" (เช่น ผลบอล, goal events) ต้องไม่อยู่ document/object เดียวกับ field ที่ "แก้ได้เฉพาะ admin และนานๆ ครั้ง" (เช่น สถานะลีก)

**เหตุผล:** ถ้าปนกัน การเขียน field ที่เปลี่ยนบ่อยจะพ่วงค่า field ที่ไวต่อสิทธิ์ที่อาจค้าง/เก่าอยู่ในหน่วยความจำของ client ไปด้วยโดยไม่ตั้งใจ และ Security Rules จะเขียนแยกสิทธิ์ตาม path ได้ยาก ถ้า field คนละสิทธิ์ปนอยู่ document เดียวกัน

## 3. ใช้ Firestore Transaction แทนการเขียนระบบ merge เอง

สำหรับ write ที่มีโอกาสชนกัน (2 session เขียนพร้อมกัน เช่น ยืนยันประมูล) ให้ใช้ `runTransaction()` ของ Firestore แทนการเขียน three-way merge เอง — Firestore มี optimistic concurrency control ในตัวอยู่แล้ว

ถ้าจำเป็นต้องมี local draft state (ฟอร์มที่ผู้ใช้กำลังกรอกค้าง) **ต้องแยกออกจาก "ข้อมูลที่ยืนยันแล้วจริงจาก server" อย่างเด็ดขาด** ห้ามใช้ก้อนเดียวกันเป็นทั้งค่าฐานสำหรับเทียบและ draft ที่กำลังพิมพ์

## 4. Deterministic ID สำหรับ action ที่ห้ามเกิดซ้ำ

action ที่ไม่ควรเกิดซ้ำ 2 ครั้งจาก event ต้นทางเดียวกัน (เช่น ยืนยันข้อเสนอประมูล) ให้ตั้ง document ID แบบผูกกับต้นทาง (เช่น `${auctionId}_${teamId}`) แทน ID สุ่ม — ถ้ามีการเขียนซ้ำ Firestore จะ overwrite เอกสารเดิมแทนสร้างซ้ำ ป้องกัน race condition สร้างรายการซ้ำ+นับโควตาซ้ำ

## 5. ลำดับ "เช็คเงื่อนไข" ต้องมาก่อน "บันทึกผล" เสมอ

ถ้าการบันทึกจะเปลี่ยนสิ่งที่กำลังเช็คอยู่ (เช่น เช็ค "เป็นแชมป์ครั้งแรกไหม" ก่อนบันทึกลง archive) ต้องเช็คเงื่อนไขให้เสร็จก่อนเขียนข้อมูลเสมอ ห้ามเช็คหลังบันทึกเพราะจะเจอข้อมูลที่เพิ่งเขียนไปแล้วในผลลัพธ์

## 6. Identity ต้องถูกบันทึก ณ ขณะเกิดเหตุการณ์

ถ้าความสำเร็จ/สถิติผูกกับ "คน" (เช่น ผู้จัดการทีมที่ได้แชมป์) ต้องบันทึกชื่อ/identity ของคนนั้น ณ ขณะเกิดเหตุการณ์จริงไว้ในเอกสาร ไม่ใช่ derive จากข้อมูลปัจจุบันย้อนหลัง (เพราะถ้าเปลี่ยนคนคุมทีมไปแล้วจะย้อนกลับไปหาไม่ได้)

## 7. Security Rules ต้องเช็คทั้ง "ใคร" และ "อะไร" เสมอ

ห้าม `allow write: if true` หรือเทียบเท่าเด็ดขาด ไม่ว่าจะดูสะดวกแค่ไหนตอนพัฒนา ทุก write path ต้องเช็ค `request.auth != null` ร่วมกับ role/ownership ที่เหมาะสมกับ field นั้น (ดูข้อ 2 — เหตุผลที่ต้องแยก field ตามสิทธิ์)
